# AI 开发模式总结

## 目标

让 MochiDock 在跨对话、跨 Agent 和长周期开发中保持连续性，同时保留用户作为项目经理、产品负责人和最终决策者的角色。

## 信息分层

- 代码与测试是可验证事实。
- 项目文档记录已经确认的共识。
- Skill 保存同类任务可复用的工作方法。
- Handoff 保存一次具体任务的现场状态。
- 聊天记录用于临时分析，不作为唯一的长期记忆。

## 工作方式

1. 开始任务时，先读取项目规则、规划、Git 状态和相关代码，核对当前事实。
2. 将新想法归入“当前正在做 / 下一步可能做 / 想法池”，不要自动扩大当前阶段。
3. 把当前阶段转化为可体验、可验证的小目标，并明确本阶段不做什么。
4. 普通实现细节可在已授权范围内推进；产品方向、隐私、持续成本、重要依赖、数据保存、发布和大规模重写必须由用户确认。
5. 阶段结束时汇总已完成、验证结果、风险、阻塞、下一步和待确认事项。
6. 在上下文质量下降或阶段自然结束时生成 Handoff，由接管者通过代码、Git 和测试重新核对，而不是盲信交接文本。
7. 只有当方法确实会重复使用时才沉淀为 Skill，避免为每个角色或临时任务建立 Skill。

## Handoff 触发条件

- 一个明确阶段已经完成。
- 对话中累积了大量代码、日志或失效方案。
- Agent 开始重复调查、遗忘约束或无法稳定说明状态。
- 修改范围逐渐偏离原任务。
- 下一阶段需要不同的专业能力。
- 即将进行重构、迁移、发布等高风险操作。

理想交接点是：阶段完成 → 代码稳定 → 完成验证 → 生成 Handoff → 新 Agent 核对后接管。

## Handoff 最低内容

1. 任务目标和允许范围。
2. 已完成内容。
3. 当前代码、分支、worktree 和 Git 状态。
4. 已确认的产品与业务规则。
5. 关键技术决策及被排除方案。
6. 修改文件、接口和数据结构变化。
7. 已执行的验证及结果。
8. 未完成内容、风险、阻塞和待确认事项。
9. 新 Agent 的接管步骤和启动指令。
10. 事实、推测、建议和待用户决定事项的明确区分。

## 最典型的 Skill 使用例子

用户会说：

> 我想到给桌面宠物加入提醒、聊天和文件整理功能。请帮我判断下一阶段先做什么，整理成一个小而可验证的计划，但不要替我决定产品方向，也不要马上开始写代码。

Skill 应该完成：

- 先读取 MochiDock 当前规划和实际项目状态。
- 将三个想法分别归类，不把它们全部加入当前范围。
- 结合当前产品阶段，提出一个最小验证目标、成功标准和明确的非目标。
- 标出需要用户决定的产品问题，并解释各选择的影响。
- 更新项目规划与进度记录。
- 在用户确认前不实施功能，也不擅自选择核心产品方向。

## 适用边界

该模式适合项目规划、范围控制、阶段复盘、Handoff 和接管验证。它不替代具体领域的实现 Skill，也不直接决定视觉方向、核心功能、隐私政策或商业模式。
