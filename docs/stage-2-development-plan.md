# MochiDock 阶段 2 开发计划（提案）

> 状态：MD-009 已完成人工验收；MD-010 已通过启动前复核并进入开发。

## 规划原则

- 先解决每天使用时真实可感知的摩擦，再增加新的动作或功能。
- 每次只安排一个可独立体验、可撤销、可验收的小任务。
- 自动测试负责稳定性和边界，真实桌面体验由用户最终验收。
- 不以“功能数量”作为进度；以用户是否愿意持续让宠物留在桌面上作为阶段 2 的主要判断。
- 新权限、隐私、数据保存、持续成本、重要依赖、发布和大规模重写必须先由用户确认。

## 当前基线

MD-001 至 MD-009 已完成。当前产品已经具备：透明单面板、拖动、五档尺寸、趴姿待机、呼吸、眨眼、点击回应、有限鼠标接近回应、动态 Hide/Show、尺寸与位置持久化，以及英文和简体中文本地化。

工程边界目前清晰：产品 Swift 文件最大 266 行，没有进入 500–600 行警戒范围；现阶段不需要为了后续开发先做重构。

## 1. 当前工作

### MD-009：记住宠物位置并安全恢复（已完成）

**用户目的**

用户把宠物拖到喜欢的位置后，退出并重开 MochiDock 不必重新摆放；外接屏断开、分辨率或可用区域变化时，宠物不会恢复到屏幕外。

**最小可测试体验**

1. 用户拖动宠物并松手后，保存最后位置。
2. 正常退出再启动，宠物直接出现在上次位置，不先闪到屏幕中心。
3. 如果原屏幕或原可用区域不存在，将宠物完整收回当前可用屏幕范围。
4. 五档尺寸切换后仍以当前中心附近安全显示，并更新可恢复位置。
5. Hide/Show 只隐藏和恢复同一面板，不覆盖已保存位置。

**成功证据**

- 自动测试覆盖拖动结束保存、首次启动默认位置、有效位置恢复、无效数据回退、屏幕变化后的安全收回、尺寸变化及 Hide/Show 不变量。
- 干净 Debug 构建和现有完整测试继续通过。
- 用户在单屏和可用的多屏场景完成退出重启、拔掉外接屏或改变屏幕布局的人工体验检查。

**明确不做**

- 不保存鼠标轨迹、动画进度、mood 或当前接近状态。
- 不同步到 iCloud，不引入 SwiftData、Core Data、网络或第三方依赖。
- 不增加自由吸附、自动走动、跨屏追逐或复杂窗口布局系统。
- 不顺带做设置页、开机启动或新动作。

**主要风险与控制**

- macOS 屏幕坐标可能为负数，屏幕排列和菜单栏/Dock 会改变可用区域；恢复时必须根据当前 `visibleFrame` 校正，而不能只验证坐标是数字。
- 频繁拖动过程中持续写偏好没有必要；首轮只在拖动结束或明确位置提交点保存。
- 位置恢复不能破坏现有 `.canJoinAllSpaces`、同一面板复用和尺寸切换的原子绘制边界。
- 本任务的“收回屏幕内”只处理屏幕配置变化、无效保存值等异常恢复；未来若实现宠物主动藏到屏幕边缘，必须作为显式动画状态处理，不能被安全校正逻辑误判为异常位置。

**需要用户确认**

- 已确认并完成验收。正式任务书见 [MD-009](tasks/completed/MD-009-pet-position-persistence-and-safe-restoration.md)。

## 2. 可能的下一步

MD-010 已由用户确认并形成任务；后续收口试用仍不预先分配新编号。

### MD-010：低打扰控制与登录时启动（开发中）

**目的：** 让用户可以关闭鼠标接近回应，同时保留角色、基础点击互动和低频待机动作。

**最小体验：** 菜单中提供一个清晰的主动回应开关；关闭后停止接近检测并保持低频待机，重启后记住选择。

**成功证据：** 开关即时生效、状态可恢复、关闭时没有接近采样、现有点击/拖动/Hide/Show 不受影响。

**非目标：** 不建立完整设置窗口，不提供大量动作频率滑杆，不加入免打扰时间表。

**风险：** 选项过多会过早增加产品复杂度；只有当长期使用确实感到打扰时才优先。

**已确认：** 菜单关闭的范围仅为鼠标接近回应，并保存选择；点击、呼吸和眨眼不关闭。

#### 登录时启动

**目的：** 降低每天手动打开应用的成本，并让状态更易理解。

**最小体验：** 菜单提供登录时启动开关，状态与 macOS 实际登录项一致，并可可靠启用和停用。

**成功证据：** 启用、停用和系统重启后的行为可预测；不残留重复实例，不需要额外权限。

**非目标：** 不进入发布、自动更新、签名公证或安装器工作。

**风险：** 登录项属于系统集成，必须验证不同系统状态；若用户当前愿意手动启动，则价值低于位置恢复。

**已确认：** 用户需要 MochiDock 随 macOS 登录自动启动，并将其与低打扰控制共同纳入 MD-010。

### MD-010 后续：阶段 2 收口与小范围试用（推荐）

**目的：** 验证 MochiDock 是否已经达到“愿意长期留在桌面”的程度，而不是继续凭想象增加功能。

**最小体验：** 使用固定版本进行数天真实使用，记录出现频率、打扰点、恢复问题和最想改善的一件事。

**成功证据：** 没有阻塞性稳定问题；能够从真实体验中明确选出一个下一阶段问题，或确认当前版本已经足够。

**非目标：** 不自动收集遥测，不上传使用数据，不直接公开发布。

**风险：** 没有结构化观察时，容易凭当天感受扩张范围；建议只记录少量事实，不做复杂分析系统。

**需要确认：** 是否邀请其他试用者，以及任何分发、签名、公证或反馈收集方式。

### 已确认方向：独立设置窗口（MD-010 验收后的下一候选）

**目的：** 避免状态栏菜单随着偏好增加而持续变长，把即时操作与长期设置分开。

**推荐的最小体验：** 状态栏菜单只保留“隐藏/显示宠物”“设置…”和“退出 MochiDock”；点击“设置…”打开单一设置窗口。宠物尺寸、鼠标接近回应和登录时启动移入设置窗口，并继续复用 MD-010 已建立的真实状态和持久化边界。

**成功证据：** 设置窗口可重复打开且不产生多个实例；三个现有设置即时生效、状态正确恢复；状态栏菜单明显简化；关闭设置窗口不退出应用或隐藏宠物。

**明确非目标：** 不顺带新增尚未确认的设置，不做账户、同步、插件、主题系统、复杂导航或通用设置框架。

**风险：** 若同时保留菜单开关和设置窗口控件，会形成双入口状态同步成本；推荐只在设置窗口保留长期偏好，菜单只保留高频动作。

**需要确认：** 是否采用上述最小信息架构。确认后再建立独立编号任务，不回头扩大 MD-010。

## 3. 想法池（不承诺）

- 屏幕边缘躲藏与偷看：宠物在合适时机主动藏到屏幕外，只露出脑袋偷偷观察用户，随后自行探出或返回；暂不确定触发方式、频率、停留时间或是否允许用户关闭。
- 换装、成长值、等级、互动统计和收藏系统。
- 更多角色姿势、飞行、移动、睡眠或场景化动作。
- 提醒、计时器、文件整理等小型工具能力。
- 聊天、知识库、复杂智能体和工具平台。
- AI 场景；只有在明确单一用途、隐私、成本、数据流和无 AI 降级方案后再讨论。
- 公开发布、自动更新、安装器、商店或商业化。

## 推荐顺序与停止规则

1. MD-009 已完成位置保存与安全恢复，并通过用户实际体验验收。
2. 用户已正式安排 MD-010；开发团队按任务书实现低打扰控制与登录时启动。
3. 开发交付后先进行独立复核和真实登录项人工验收，不自动视为完成。
4. MD-010 验收后，若用户确认推荐的信息架构，则单独建立设置窗口任务；完成后再长期使用当前版本，不自动进入工具、AI、成长系统或发布流程。

任何任务出现新权限、隐私风险、网络、持续成本、重要依赖、复杂数据模型或大范围结构改造时，停止扩展并请求用户决定。

屏幕边缘躲藏若未来进入探索，应先单独验证一件事：只露出脑袋时是否仍容易被发现和恢复，并且不会被误认为窗口丢失或应用故障。在此之前不并入位置保存、自动移动或其他动画任务。
