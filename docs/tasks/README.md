# MochiDock 任务文档规则

## 目的

`task_plan.md` 是项目总览和任务索引；每个可独立安排、实现和验收的开发任务使用一份独立任务书，避免总计划持续膨胀。

## 目录

- `active/`：草拟中、待安排、开发中、待验收或已阻塞的任务。
- `completed/`：已经完成验收的任务。

任务完成验收后，将任务书移入 `completed/`，并同步更新 `task_plan.md` 的任务索引和 `progress.md` 的阶段摘要。

## 编号与命名

- 编号格式：`MD-001`、`MD-002`，按用户批准进入任务流程的先后顺序递增。
- 文件格式：`MD-001-short-task-name.md`。
- 不为想法池提前分配编号；只有形成可安排任务后才创建任务书。

## 状态

- `草拟中`：高级项目经理正在整理，尚不可安排。
- `待用户安排`：任务书完整，等待用户交给 Codex 开发部门。
- `开发中`：用户已安排，Codex 正在实施。
- `待验收`：Codex 已提交结果，等待高级项目经理只读核对。
- `已完成`：验收通过并更新项目记录。
- `已取消`：用户明确不再执行。
- `已阻塞`：存在无法由开发部门自行解决的产品决定或外部条件。

## 每份任务书必须包含

1. 状态、负责人和任务目标。
2. 背景与用户价值。
3. 开发范围和明确非目标。
4. 可验证的验收标准。
5. 技术与项目约束。
6. 开发部门需要完成的验证。
7. 交付时必须汇报的内容。
8. 需要用户决定的事项；没有则明确写“无”。

任务书规定结果与边界，不替开发部门锁死所有实现细节。开发中若发现需要扩大范围或触发关键决策，Codex 应停止相关扩展并向用户汇报。
